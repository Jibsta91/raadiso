# 0034 — Tunnel mode: Pangolin on the laptop for public access and a VPN

- Status: Accepted
- Date: 2026-10-07

## Context

Phone mode (ADR-0022) serves the development stack to a phone on the same Wi-Fi. Testing away from home (on
mobile data, or showing the site to someone else) needs the stack on the internet. The stack keeps running
on the laptop, and we don't rent a server before Phase 5.

## Decision

- **`./raadi tunnel`** runs phone mode plus `compose.tunnel.yaml`, which adds a self-hosted
  [Pangolin](https://github.com/fosrl/pangolin) on the same laptop: Pangolin 1.24 (AGPL-3.0 community
  edition), Gerbil (WireGuard, AGPL-3.0), Pangolin's Traefik with the Badger plugin (MIT), and the site
  connector (newt inside the Pangolin CLI, AGPL-3.0). All run unmodified as separate services, like Grafana
  (ADR-0009). The enterprise edition (Fossorial Commercial License) is not used.
- **Networking.** Gerbil publishes TCP 80/443 and UDP 51820/21820 on the laptop's LAN address, and the home
  router forwards those ports to it. The LAN address and the home network's public address are found by
  the command (`LAN_IP` and `PUBLIC_IP` override them). Our gateway stays on 127.0.0.1. Pangolin's
  components live on their own `tunnel` network; only `pangolin-site` joins both networks, so the only way
  from Pangolin into the stack is the WireGuard tunnel to it. It shares a small `edge` network with our
  gateway alone, so it cannot reach any other service.
- **DNS and TLS.** `dev.raadiso.com` and `*.dev.raadiso.com` (phone mode's name), and the dashboard's
  `pangolin.raadiso.com`, point at the home's public address (GoDaddy API, ADR-0023). Pangolin's Traefik
  uses the Let's Encrypt wildcards from our DNS-01 job, in a volume of their own, so its certificates don't
  depend on port 80 and it never sees the development CA. Inside the stack, `pangolin.raadiso.com` is a
  network alias of Gerbil, so the site connects without going round the router.
- **What is public.** Three Pangolin public resources, each behind Pangolin's own sign-in: the website and
  API (`dev.raadiso.com`), sign-in (`auth.dev.raadiso.com`, with Keycloak's `/admin` refused) and test
  payments (`pay.dev.raadiso.com`). The demo passwords are public in this repository, so nothing is open
  without a Pangolin account.
- **What is VPN only.** Two private resources give a device signed in to the Pangolin app (iOS, Android,
  macOS, Windows, Linux) `dev.raadiso.com` and `*.dev.raadiso.com` straight to our gateway: the admin
  console and the dev tools included, and Metro as `https://metro.dev.raadiso.com` (a gateway route that
  exists only in tunnel mode; iOS development builds refuse plain http to a host name). The
  native app talks to the API through the VPN, because it cannot pass a sign-in page in front of an API.
  Metro is never public: its dev server has had remote-code-execution bugs.
- **Set up as code.** Pangolin reads a setup token from the environment. A one-shot `pangolin-init` job
  uses it to create the admin, then signs in as the admin to create the organisation and the laptop's site
  (with site credentials we generate) and to apply `deploy/pangolin/blueprint.json.tmpl`. The integration
  API stays off (a root API key from the environment gets no permissions in 1.24 anyway).
  The resources always match the repository, and a cold start needs no clicks. Pangolin's secrets come from
  secrets-init; the admin password is generated by `pangolin-config` because Pangolin requires upper case, a
  digit and a symbol (`./raadi secret pangolin_admin_password`).
- **`./raadi up` closes the tunnel.** `up`, `phone` and `tunnel` remove services the chosen files don't
  define, so Pangolin's public edge stops when you switch back.

## Alternatives considered

- **Pangolin on a rented server (VPS or AWS):** works wherever the laptop is and keeps the home address out
  of DNS, but costs money and is a second machine to run before Phase 5. The same files move to a server
  later: only the site connector stays on the laptop.
- **Pangolin Cloud:** no server or port forwarding, but a third-party service holding the traffic and an
  account key (ADR-0009).
- **Cloudflare Tunnel, ngrok, Tailscale Funnel:** hosted relays with accounts; against running offline and
  OSI first. Expo's own tunnel (ngrok) was rejected in ADR-0022 for the same reason.
- **Plain WireGuard or Headscale for the VPN plus port forwarding to our gateway:** two systems instead of
  one, and the website would be public with no sign-in in front.
- **Only a VPN:** simplest, but nobody without the app could open the site.

## Consequences

- Needs a public IPv4 address from the ISP (no carrier-grade NAT) and the router's port forwarding. It
  works only while the laptop is on that network, and the address can change: run `./raadi tunnel` again
  to update DNS.
- The home's public address is in public DNS while tunnel mode is in use (it stays there afterwards until
  the record changes).
- All tunnel traffic reaches our gateway from one address (the site connector), so the gateway's per-client
  rate limits are shared by everyone using the tunnel, as with the Playwright workers.
- Resources added by hand in the dashboard can reach only the gateway (the site connector sees nothing
  else). The blueprint overwrites them only when names collide, and doesn't delete resources it no longer
  lists: remove those in the dashboard.
- Pangolin's image is large (≈ 1.6 GB) and the tunnel adds ≈ 0.5 GB of memory. It is not part of the default
  stack or of the budget in ADR-0011.
- Traefik downloads the Badger plugin at start, and Pangolin checks its model catalogue online. Tunnel mode
  needs the internet anyway.
